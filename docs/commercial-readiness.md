# 商用牙科 CT/CBCT 工作台：许可证与医疗软件合规审查

> 审查日期：2026-10-23  
> 审查范围：`code/ct-workbench` 当前依赖、已声明的产品方向，以及中国大陆牙科诊所场景  
> 文档性质：工程与合规差距分析，不是法律意见、监管决定、检测报告或注册咨询结论

## 1. 先把三类信息分开

- **[事实]**：可从当前项目、法律文本、监管文件或上游许可证直接核对的信息。
- **[建议]**：为降低发布风险可采用的工程、文档或流程措施。
- **[待确认]**：需要注册顾问、律师、检测机构或监管沟通确认的问题。本文不能替代这些专业判断。

本文不会得出“已经合规”“可直接用于正式诊断”“必然属于某一医疗器械类别”等保证性结论。

## 2. 本次审查基线

### 2.1 已核对的项目事实

- 项目名称为 `dental-ct-workbench`，当前版本为 `2.4.0`，`package.json` 将自身标为 `UNLICENSED`。
- 当前直接依赖包括 Electron、React、React DOM、Vite、`@vitejs/plugin-react`、`dicom-parser`、`adm-zip`、`lucide-react` 和 `electron-builder`。
- 初次读取项目时还没有 `package-lock.json`；并发开发随后生成了 lockfile v3。本次复核的 SHA-256 为 `88B5E971DEB65324099DFDB826821BD8BA440A127E03D89642F47B1E62CF6FE3`，后续任何依赖变化都必须重新生成 SBOM、许可证清单和该哈希。
- lockfile 中有 327 个带版本的包条目，许可证字段缺失数为 0。其中 325 个被 npm 标为开发依赖，但 React、React DOM、Lucide 等会打进渲染产物，Electron 运行时会作为平台二进制分发，因此不能用 `devDependencies` 标记代替最终“随产品分发”清单。
- `adm-zip` 声明为 `^0.5.16`，当前锁定版本为 `0.5.18`，说明最终版本必须从 lockfile/SBOM 读取，不能从 `package.json` 的版本范围推断。
- 项目规划包含 Cornerstone3D，但审查时 `@cornerstonejs/core` 和 `@cornerstonejs/tools` 尚未出现在 `package.json` 中。
- 导入设计会按 DICOM Study/Series 分组，并把原始 DICOM 文件复制到本机病例库。
- 当前本地病例清单会生成匿名显示名和编号，但复制进病例库的原始 DICOM 文件仍可能完整保留患者姓名、编号、生日、设备、机构、日期、UID、私有标签和像素内文字等身份信息。
- 当前设计没有网络传输影像，但安装、更新、授权、日志上传或远程支持一旦联网，就需要重新评估网络与数据合规边界。
- 本次只审查许可证与合规控制，不是完整安全渗透测试，也不是测量准确性验证。

### 2.2 产品定位事实与边界

项目面向两类用途：

1. 临床阅片和测量辅助。
2. 病例沟通、展示和术前初步讨论。

“技术可发布”与“作为正式诊断医疗器械发布”不是同一门槛。一个可安装、可导入、可展示的软件可以具备商业发布的技术形态，但若在宣传、说明书或销售场景中声称用于诊断、治疗决策或正式临床测量，就可能进入医疗器械监管范围。

## 3. 总体结论

### 3.1 技术可发布的最低含义

[事实] 软件在技术上可以完成安装、导入、显示、测量、保存和卸载，并且可以附带第三方许可证。

[建议] 若首阶段不宣称诊断用途，可以把它定位为“本地影像查看、病例沟通和初步测量工具”，同时明确它不是诊断结论生成器。该定位是否足以排除医疗器械属性，不能由工程团队自行决定。

### 3.2 正式诊断医疗器械发布

[建议] 若产品面向医院或诊所宣称用于正式阅片、诊断、术前决策或影响临床决策的测量，应将项目按软件医疗器械/SaMD 候选产品管理，先完成分类界定和监管路径确认，再冻结预期用途、风险管理、软件生存周期、验证确认、网络安全、临床评价和上市后体系。

[待确认] 产品在中国大陆按第几类医疗器械管理、是否需要注册或备案、是否可适用临床评价豁免、是否构成独立软件或软件组件，需要结合预期用途、核心功能、算法、用户和风险由专业注册顾问或监管部门确认。不能仅凭“牙科”“离线”“不带 AI”推断分类。

## 4. “技术可发布”与“正式诊断发布”的差距

| 领域 | 技术可发布所需 | 正式诊断发布通常还需 | 当前证据状态 |
| --- | --- | --- | --- |
| 预期用途 | 明确能做什么、不能做什么 | 受控的预期用途、适应证、禁忌证、目标用户和使用环境 | 需形成正式受控文件 |
| 产品分类 | 不宣称医疗器械功效 | 分类界定结论及注册/备案路径 | 未确认 |
| 质量管理体系 | 有发布与回滚流程 | 与产品风险相适应的全生命周期质量管理体系 | 未提供证据 |
| 风险管理 | 记录主要产品风险 | 系统化风险分析、风险控制、剩余风险和受益风险评价 | 未提供完整文件 |
| 软件生存周期 | 需求、代码、测试、版本可追踪 | 受控的需求、架构、设计、实现、测试、发布、维护和配置管理 | 当前有部分测试，仍需完整追踪 |
| 验证与确认 | 能证明主要流程可用 | 形成验证报告、用户需求确认、可用性和人因评价 | 需补齐代表性病例和边界条件 |
| 测量准确性 | 显示预期误差和限制 | 在定义条件下验证距离、角度、HU、ROI 等精度和重复性 | 需建立参考基准与容差 |
| 临床评价 | 不以临床有效性作宣传 | 同品种比对、文献/临床数据评价，必要时临床试验 | 未开展或未提供证据 |
| 网络安全 | 最小权限、受控导入、安全更新 | 网络安全能力、威胁建模、漏洞管理、渗透测试和事件响应 | 未提供完整证据 |
| 隐私保护 | 本地处理、最少收集、清晰说明 | 个人信息处理规则、权限、加密、保留删除、备份和审计 | 需结合诊所实际流程确认 |
| DICOM 去标识 | 展示模式不泄露直接身份信息 | 按用途定义去标识规则，覆盖标签、私有标签、像素和关联对象 | 当前清单匿名不等于 DICOM 去标识 |
| 数据完整性 | 原子写入与基本错误提示 | 备份恢复验证、审计追踪、权限分离和故障恢复 | 需形成可验证流程 |
| 更新与变更 | 稳定安装和版本显示 | 变更分类、回归验证、签名更新、可追溯发布和回滚 | 未提供完整机制 |
| 代码签名 | 可选但强烈建议 | 正式发布通常应有可验证签名、时间戳和发布链 | 未提供证书与签名证据 |
| 用户文档 | 操作说明和限制 | 说明书、标签、已知问题、禁忌和风险提示 | 需形成正式版本 |
| 上市后管理 | 反馈渠道 | 不良事件、投诉、召回、漏洞响应和定期风险复盘 | 未提供完整机制 |

## 5. 中国大陆监管与法务要点

### 5.1 医疗器械与软件注册

[事实] 《医疗器械监督管理条例》要求医疗器械研制、生产、经营和使用活动遵守全生命周期管理要求；《医疗器械注册与备案管理办法》规定第一类医疗器械备案、第二类和第三类医疗器械注册，并要求注册资料覆盖风险分析、产品技术要求、检验、临床评价、说明书标签和质量体系文件。

[事实] 国家药监局器审中心 2022 年第 9 号通告发布了《医疗器械软件注册审查指导原则（2022 年修订版）》；2022 年第 7 号通告发布了《医疗器械网络安全注册审查指导原则（2022 年修订版）》。这些文件是软件研究、网络安全资料和审评准备的重要依据，但不能替代针对本产品的分类和注册判断。

[建议]

- 在开发早期冻结“临床模式”和“展示模式”的预期用途、功能边界和不可宣称事项。
- 就牙科 CBCT 阅片、距离/角度/HU/ROI 测量、多平面重建和匿名展示是否构成医疗器械功能，向专业注册顾问或监管部门做书面沟通或分类界定。
- 将“正式诊断”与“非诊断展示”拆分为可审计的产品模式、用户文档和宣传口径，不能只靠界面中的一句免责声明区分。
- 把软件完整版本号、发布标识、更新记录和产品技术要求纳入配置管理。
- 确认独立软件/软件组件的产品标识、版本标识、标签和适用 UDI 要求；不要把版本号视为 UDI 的替代。

### 5.2 软件生存周期与质量管理

[事实] `GB/T 42061-2022`（医疗器械质量管理体系）和 `GB/T 42062-2022`（医疗器械风险管理）现行；医疗器械软件指导原则强调软件生存周期、需求与设计、验证确认、可追溯性、缺陷管理和版本控制。

[建议]

- 建立受控需求编号，并让设计、代码、测试、缺陷、风险控制和发布记录相互追踪。
- 为导入、解析、匿名化、测量、保存、删除、备份、恢复和更新分别定义验证证据。
- 建立软件问题分级、回归测试、发布门禁和紧急修复流程。
- 每次构建保存 `package-lock.json`、SBOM、制品 SHA-256、签名结果、测试报告和变更说明。
- 将第三方组件升级纳入变更控制；不能被自动更新绕过回归或监管评估。

### 5.3 风险管理与临床验证

[建议]

- 按产品全生命周期建立风险管理文件，至少覆盖：错误患者匹配、错误层序、像素间距或方向错误、测量单位错误、ROI 统计失误、去标识不彻底、病例丢失、损坏文件、恶意 ZIP、权限绕过和错误更新。
- 测量验证应使用已知几何尺寸的体模、厂家提供的元数据和经授权的人工标注，不应只用合成单元测试证明临床精度。
- 临床评价应覆盖代表性设备、层厚、像素间距、金属伪影、种植体、缺牙、儿童/成人、不同 FOV、压缩 DICOM、DICOMDIR、ZIP 和多序列病例。
- 对临床模式与展示模式分别做用户确认，不能把“界面能操作”当作“临床可用”。
- 建立容差和不适用条件。例如测量误差、HU 偏差、方向标记、插值策略、最小层数和显示器要求必须写入说明书和测试报告。

[待确认] 是否可免于临床评价、需要同品种比对还是临床试验，以及临床终点、样本量和统计方法，必须由专业注册路径决定。

### 5.4 网络安全与软件更新

[事实] 医疗器械网络安全指导原则要求在产品全生命周期考虑保密性、完整性、可得性、授权、审计、漏洞管理和更新安全。离线不等于不存在风险，U 盘、光盘、ZIP、共享目录、恶意 DICOM、供应链和安装包都可成为攻击入口。

[建议]

- 建立威胁模型，覆盖文件导入、ZIP 解压、DICOM 解析、路径处理、IPC、渲染进程、更新、日志和本地病例库。
- Electron 保持 `contextIsolation: true`、`nodeIntegration: false`、沙箱和最小 preload API；禁止把任意文件系统能力暴露给渲染层。
- 对 ZIP 设置压缩比、单文件大小、总解压大小、条目数和路径规范化限制，防止 ZIP bomb 和路径穿越。
- 对 DICOM 解析设置文件大小、元素长度、嵌套深度和像素数据上限，畸形输入应可恢复失败。
- 建立 SBOM、依赖漏洞扫描、许可证扫描和已知残余漏洞清单。
- 更新必须使用签名清单、哈希校验、防降级和明确回滚；正式诊断版本不应无提示静默更新。
- 建立漏洞接收、分级、修复、披露和客户通知流程。

### 5.5 个人信息、健康数据和诊所流程

[事实] 医疗健康信息通常属于敏感个人信息。《中华人民共和国个人信息保护法》要求处理敏感个人信息具有特定目的和充分必要性，并采取严格保护措施；法律法规另有规定时，应依相应规定确定合法性基础。DICOM 头信息、检查日期、设备机构信息、影像像素和测量记录都可能与个人关联。

[建议]

- 明确诊所是个人信息处理者还是受托处理者，软件厂商是否接触数据，以及远程支持是否会接触真实病例。
- 默认本地处理，不上传影像、患者姓名、原始 UID、测量内容或崩溃转储。
- 若提供诊断用途，必须定义数据保留期限、删除流程、导出目的、备份保留和诊所离场后的数据处理。
- 对本地病例库采用 Windows 用户隔离和访问控制；共享电脑上应增加应用级用户身份或明确禁止多用户共用。
- 对静态数据保护、密钥管理和备份加密做威胁评估。仅在文档中声称“加密”而无法验证，不构成有效控制。
- 遥测和崩溃报告必须默认关闭或明确同意，并做字段白名单、去标识和传输加密。

[待确认] 具体合法性基础、隐私告知、授权文本、数据保留期限和受托处理协议，需要结合诊所部署方式由法律/隐私顾问确认。

### 5.6 DICOM 隐私与去标识

[事实] DICOM PS3.15 Annex E 明确说明：仅按隐私配置处理属性并不保证对象整体已完成去标识。直接标签、私有标签、图形注释、结构化报告、缩略图、波形、文件元信息和像素中的烧录文字都可能泄露身份。

[建议]

- 将“清单显示名称匿名”与“DICOM 文件去标识”作为两个不同能力，不可混为一谈。
- 展示模式导出前执行专门去标识流程，至少覆盖患者、人员、机构、日期时间、UID、访问号、私有标签、图形/覆盖层、结构化报告和像素烧录文字。
- 在 DICOM 中正确记录 `PatientIdentityRemoved`、`DeidentificationMethod` 和适用的方法代码；不要仅删除几个文本标签就宣称匿名化。
- 去标识前后生成技术日志，记录规则版本、处理文件数、残留风险、目视抽查和失败项，但日志本身不得包含被删除的原始身份信息。
- 提供“原图保留、展示副本去标识”的不可混淆工作流；覆盖文件名、最近打开列表、崩溃日志和缩略图缓存。
- 对像素内文字无法安全去除的病例，阻止导出并要求人工处理。

[待确认] “匿名化”是否能达到法律上的不可识别、关联风险是否可接受，需要结合共享目的、接收方和可获得的辅助信息由隐私专业顾问判断。

### 5.7 审计日志、备份和删除

[建议]

- 审计事件至少包括：导入、打开、模式切换、测量新增/修改/删除、导出、去标识、删除、备份、恢复、更新、登录/解锁和失败事件。
- 日志记录时间、应用版本、Windows 用户标识、病例内部键、操作结果和必要错误码；尽量避免记录患者姓名、原始 UID 和不必要的自由文本。
- 对日志做追加写入、完整性校验和保留策略。若产品宣称“防篡改”，必须用可验证机制证明，例如链式哈希或外部不可变日志。
- 病例删除前显示范围，明确是否同时删除备份、缓存、测量和回收站副本；SSD 上的安全擦除不能简单等同于删除文件，应如实说明限制。
- 提供手动备份、完整性校验和恢复演练。只有成功恢复并通过病例与测量核对，才能认为备份有效。
- 更新、迁移或恢复失败时应保留原库，不覆盖唯一副本。

### 5.8 代码签名、安装、发布和供应链

[建议]

- 使用受控代码签名证书签署安装包、主程序和更新清单，并使用可信时间戳。
- 验证签名链、发布哈希和版本信息；构建机与私钥隔离，签名操作留痕。
- 没有商业证书时，应明确提示“未知发布者”，不能宣传为“受信任发布者”或“已消除 SmartScreen 警告”。
- 安装包只包含锁定依赖、生产资源和必要许可证，不夹带病例、开发密钥、测试影像、源码映射或调试日志。
- 对构建产物做恶意软件扫描、依赖漏洞扫描、许可证扫描和安装/卸载/升级/回滚冒烟测试。
- 建立发布冻结、双人复核和撤回流程；撤回后提供安全降级或数据迁移方案。

### 5.9 用户协议、说明书和免责声明

[建议]

- EULA 应说明软件版本、授权范围、数据责任、备份责任、第三方组件、出口/再分发限制、支持期限和终止条件。
- 说明书应说明预期用户、目标环境、支持的 DICOM 类型、已知限制、测量误差、不得替代医生判断、数据备份与隐私责任。
- 免责声明不能替代注册、临床评价、网络安全或隐私合规，也不能消除虚假宣传风险。
- 若作医疗器械销售，广告和宣传用语应经过法规审核；不能使用未经批准的适应证、诊断性能或“AI 自动诊断”等卖点。

## 6. 第一阶段可落地的技术控制清单

### P0：进入任何外部试用前

1. **固定并验证可复现依赖基线**  
   提交并保护当前 `package-lock.json`，在 CI 使用 `npm ci`；每次构建记录其 SHA-256，禁止以浮动 `^` 版本直接生成正式安装包。

2. **建立 SBOM 与许可证门禁**  
   每次发布生成 CycloneDX 或 SPDX SBOM，扫描直接和传递依赖；发现未知许可证、GPL/AGPL 等高风险许可证时阻断发布，并由法律顾问审核。

3. **生成完整第三方通知包**  
   自动收集所嵌入版本的版权行和完整许可证文本，随安装包分发；必须包含 Electron 内嵌的 Chromium、Node.js 及其第三方通知。

4. **建立明确的两种模式**  
   展示模式默认去标识并禁止诊断宣传；临床模式显示原始身份与临床资料，并要求受控用户、审计和备份。销售截图、演示病例和支持记录也不得使用未经授权的可识别影像。

5. **对输入解析做硬限制**  
   限制路径深度、文件数、DICOM 数、ZIP 条目数、单文件大小、总解压大小和压缩比；拒绝路径穿越、符号链接越界和异常 DICOM 长度。

6. **保护唯一数据副本**  
   导入使用临时目录和原子落库；删除前确认；保存测量使用原子替换；建立最小可用的备份与恢复流程。

7. **建立最小审计日志**  
   记录导入、查看、测量变更、导出、去标识、删除、备份、恢复和更新，不写入不必要的患者身份信息。

8. **建立发布制品控制**  
   发布包记录 SHA-256、SBOM、测试报告、许可证清单和已知问题；安装包中不得包含真实病例、密钥或测试数据。

9. **写明能力边界**  
   在 README、软件关于页、EULA 和销售资料中区分“查看/沟通/初步测量”与“正式诊断”，不提供未经证实的准确性、兼容性或合规声明。

### P1：进入诊所试点前

1. 对导入、测量、去标识、删除和恢复做代表性病例验证。
2. 建立威胁模型和依赖漏洞扫描，处理高危问题。
3. 为本地病例库定义 Windows 用户隔离、权限和共享电脑禁用策略。
4. 为备份、恢复、日志完整性和密钥管理做故障演练。
5. 提供中文操作手册、已知限制、支持渠道和问题上报模板。
6. 与试点诊所签署清晰的数据角色、保密、支持和事件响应协议。
7. 对展示导出做像素内文字和私有标签抽查，不能用自动化通过率替代人工复核。
8. 冻结测量算法、显示算法和 DICOM 解析策略的版本，并建立回归样本库。

### P2：以正式诊断医疗器械发布前

1. 完成分类界定和监管路径确认。
2. 建立并运行与产品风险相适应的质量管理体系。
3. 完成受控需求、设计、验证、确认、可追溯性和缺陷管理。
4. 完成风险管理、软件研究、网络安全研究和产品技术要求。
5. 完成临床评价，必要时开展临床试验。
6. 完成说明书、标签、广告和用户培训材料审核。
7. 完成代码签名、受控更新、漏洞响应和上市后监测体系。
8. 完成注册检验、体系核查和注册申请所需的全部资料。

- “绝对安全”“零数据泄露”“防勒索”

## 8. 需要专业法律/法规顾问确认的问题

1. 本产品的临床模式和展示模式是否分别构成医疗器械，是否可按不同产品发布。
2. 牙科 CBCT MPR、距离、角度、HU 和 ROI 测量在预期用途下属于何种风险类别。
3. 是否需要注册、备案或变更注册，是否适用临床评价豁免或同品种比对。
4. 诊所与软件厂商在《个人信息保护法》下的角色、合法性基础、告知同意和受托处理责任。
5. 去标识导出能否称为匿名化，以及展示、教学、跨机构会诊的合规边界。
6. 离线软件涉及的光盘、U 盘、ZIP 和本地备份是否落入特定网络/数据安全规则的适用范围。
7. 电子签名、审计日志和测量记录的保存年限及证据效力。
8. 软件许可、订阅、一次性销售、硬件捆绑和云服务的经营/售后责任。
9. EULA、隐私政策、SLA、医疗器械广告和跨境支持的文本。
10. 软件重大更新、算法变化和第三方组件替换是否触发注册变更或重新验证。

## 10. 审查结论摘要

- **可以继续做技术开发和受控试用，但不能把当前版本直接宣称为可正式诊断的医疗器械。**
- 当前最重要的工程缺口是：固定并验证依赖基线、生成完整第三方许可证包、形成可复现构建、补齐去标识边界、建立审计/备份/更新控制。
- 当前最重要的监管差距是：分类与预期用途未确认、质量体系与风险管理未形成完整证据、临床评价和网络安全验证未完成。
- 合规结论应以分类界定、检测、临床评价、体系核查、注册审批以及法律/隐私审查的实际结果为准。
